8. Deployment & infrastructure

One Ubuntu 24.04 VPS on Alibaba Cloud (Singapore), shared with the Innov8tif site. Caddy in front, PHP 8.4-FPM, Supervisor for the queue worker, SQLite on disk. Deploys are pushed from a laptop with Deployer.

The deploy, in order

dep deploy prod runs deploy.php Custom on top of Deployer's Laravel recipe Addon: Deployer:

  1. Clone the branch with Git LFS smudging skipped, then lfs:pull runs git lfs pull for the videos; if that fails it copies them from the live release and refuses to continue if any LFS pointer file is left. Link .env and the shared dirs (data/sqlite, data/media, data/backups).
  2. composer install, then storage:acl (see below). Its post-autoload-dump script runs statamic:install, which publishes the control panel's and the toolkit's assets to public/vendor/ (git-ignored). Update scripts don't run here: they need the composer.lock.bak that only composer update writes.
  3. npm install and npm run build (hung off deploy:vendors).
  4. db:ensure-sqlite → db:backup (copy, keep 5) → migrate:safe (backs up again if migrations are pending).
  5. Storage links (public/media → shared/data/media), then content:import: pixaproof:import-content --once. The first deploy creates the content; every later deploy does nothing, so control panel edits are kept. The import must come after the links: storage:link-custom replaces public/media, which deleted the images the first production deploy had copied there.
  6. Maintenance mode on → switch the current symlink → restart PHP-FPM → maintenance mode off → restart the queue worker → rebuild caches → stache:warm.
  7. deploy:verify requests the site up to five times; on failure the release is rolled back.

storage:acl exists because of the first production deploy (2026-10-07), which returned 500 on every request. shared/storage carries default ACLs for www-data, but Statamic creates storage/statamic/* with mkdir(…, 0755), which sets the ACL mask to r-x and caps www-data at read-only ("FlockStore directory … is not writable"). The task restores the mask on everything deployer owns, after composer install and again after the Stache warm. The same deploy also exposed that the automatic rollback had never worked: a second fail('deploy', …) replaced the first handler. Both tasks now hook the recipe's deploy:failed.

The build-backup-migrate chain hangs off deploy:vendors. Until 2026-10-07 it hung off artisan:config:cache, which ran twice (once from an extra hook, once in the recipe's own list), so every deploy built the assets, backed up and migrated twice.
