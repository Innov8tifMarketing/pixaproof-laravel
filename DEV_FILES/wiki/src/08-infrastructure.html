8. Deployment & infrastructure

One Ubuntu 24.04 VPS on Alibaba Cloud (Singapore), shared with the Innov8tif site. Caddy in front, PHP 8.4-FPM, Supervisor for the queue worker, SQLite on disk. Deploys are pushed from a laptop with Deployer.

{{diagram:deploy}}

The deploy, in order

dep deploy prod runs [[deploy.php]] {{C}} on top of Deployer's Laravel recipe {{A:Deployer}}:

  1. Clone the branch with Git LFS smudging skipped, then lfs:pull runs git lfs pull for the videos; if that fails it copies them from the live release and refuses to continue if any LFS pointer file is left. Link .env and the shared dirs (data/sqlite, data/media, data/backups).
  2. composer install. Its post-autoload-dump script runs statamic:install, which publishes the control panel's and the toolkit's assets to public/vendor/ (git-ignored). Update scripts don't run here: they need the composer.lock.bak that only composer update writes.
  3. npm install and npm run build.
  4. db:ensure-sqlite → db:backup (copy, keep 5) → migrate:safe (backs up again if migrations are pending).
  5. content:import: pixaproof:import-content --once. The first deploy creates the content; every later deploy does nothing, so control panel edits are kept.
  6. Maintenance mode on → switch the current symlink → restart PHP-FPM → maintenance mode off → restart the queue worker → rebuild caches → stache:warm.
  7. deploy:verify requests the site up to five times; on failure the release is rolled back.

Steps 3–5 run twice per deploy. Deployer's Laravel recipe runs artisan:config:cache twice, and this repo chains npm:install → … → migrate:safe → content:import after it. The second run is harmless (no pending migrations, --once skips) but doubles the build time. Not changed, because it needs a real deploy to test.
